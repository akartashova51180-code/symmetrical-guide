# План проверки перед серверным запуском

Цель — подтвердить не только запуск программы, но и весь путь: запись задачи/песни → сохранение в PostgreSQL → работа Telegram → повторный запуск → восстановление резервной копии. Ни один этап не считается пройденным только потому, что контейнер показывает статус `running`.

## Этап 1. Локальная автоматическая проверка

Команда из `system/runtime`:

```bash
uv run --locked pytest -q
```

Критерий: все имеющиеся тесты проходят. Сейчас проходят 17 тестов, включая allowlist Telegram, кнопочное меню и команды, получение owner ID из частного `/start`, ввод идеи/задачи/паспорта, расписание, очередь отправки уведомлений, snapshot SQLite, миграцию старого состояния приёмщика, импорт проектов/задач и загрузку музыкальных файлов.

## Этап 2. PostgreSQL и API

На отдельной временной PostgreSQL базе проверить:

- создание схемы и импорт CSV при начальном заполнении;
- чтение, создание и обновление проекта, задачи и песни;
- загрузку/скачивание вложения; SHA-256 в карточке совпадает с файлом;
- корректную работу ID и последовательностей после вставок;
- рестарт приложения с той же базой: записи сохраняются, повторных проектов и ежедневных уведомлений нет.

Критерий: API возвращает те же контрольные записи до и после рестарта; загрузка тестового аудиофайла читается побайтно; расписание не создаёт дублей.

## Этап 3. Перенос данных

Взять согласованный snapshot SQLite и отдельную копию каталога assets. Импортировать их в пустую тестовую PostgreSQL базу, а затем сравнить:

- количество записей по каждому реестру;
- ID и содержимое выборочных проектов, задач, решений, песен, кампаний и затрат;
- количество вложений, их размеры и SHA-256;
- не больше одной актуальной записи утренней сводки в outbox для даты миграции.

Критерий: записи совпали, каждый файл существует и хеш совпадает. Исходная SQLite база остаётся нетронутой и может быть снова открыта.

Для полной проверки миграции нужен именно ваш снимок базы и media-каталог на сервере/вашем устройстве. Их не нужно отправлять в чат. Если не хочется использовать рабочие данные на тестовом этапе, сначала проверяем весь механизм на синтетическом наборе, а рабочую базу переносим только на финальном этапе с резервной копией.

## Этап 4. Telegram-приёмщик

Использовать отдельного тестового бота и только личный Telegram ID владелицы. Проверить:

- `/start` показывает меню; кнопки запускают сводку, проекты, задачи, ввод идеи, каталог и мастер паспорта;
- `/new`, `/source`, `/projects`, `/link`, `/text`, `/done` меняют только выбранный тестовый паспорт;
- аудио и текст прикрепляются к активной песне, бот возвращает song ID;
- повтор того же файла не создаёт вторую копию;
- чужой ID, групповой чат, неподдерживаемое расширение и файл больше лимита отклоняются без создания лишних записей;
- остановка API даёт понятную ошибку, а после запуска приём возобновляется без повторной загрузки уже обработанного обновления.

Критерий: только разрешённая владелица может менять CRM; каждый результат попадает ровно в ожидаемую карточку. Telegram Bot API тестируется реальным токеном только в его локальном/server `.env`; токен в тестовые отчёты и чат не попадает.

## Этап 5. Telegram-уведомления

Уведомления направлять только тестовому боту в личный чат владелицы. Проверить:

- ежедневную сводку: 09:00 по Москве; при новом запуске отправляется текущая ожидающая сводка;
- сроки сегодня и просроченные задачи;
- повестку в понедельник, среду и пятницу;
- неверный chat ID не отправляет сообщение за пределы allowlist;
- временный отказ Telegram сохраняет сообщение в PostgreSQL и повторяет отправку через очередь;
- успешная доставка помечается и не дублируется при рестарте;
- пустой реестр дохода не отображается как «доход 0 ₽».

Критерий: сообщение пришло в ожидаемый личный чат один раз; после рестарта дублирования нет; при искусственном сетевом отказе очередь сохраняет событие до успешной отправки.

## Этап 6. Сервер, безопасность и автозапуск

На временном VPS либо тестовом сервере проверить:

- `docker compose config --quiet`, успешную сборку и запуск всех трёх сервисов;
- приложение и бот перезапускаются после `docker compose restart` и перезагрузки Linux;
- PostgreSQL и приложение healthy; база не доступна с публичного адреса;
- порт 8787 доступен только локально/VPN/SSH-туннелю; PostgreSQL 5432 не опубликован;
- в Git, логах и docker-compose config output нет токена и пароля;
- потеря соединения с Telegram не завершает приложение навсегда;
- остановка одного контейнера не повреждает базу и файлы.

Приложение пока не имеет собственной аутентификации. Поэтому критерий безопасности сейчас — закрытый доступ уровнем сети (SSH/VPN ACL) и отсутствие открытого публичного доступа к панели, а не тест пользовательского пароля.

## Этап 7. Резервное копирование и восстановление

Создать backup PostgreSQL и медиа, зашифрованные ключом age. Восстановить копии в чистую отдельную базу и каталог, не поверх исходных данных. Сверить число записей, ID песен и SHA-256 файлов, затем открыть API и загрузить тестовую карточку.

Критерий: восстановленная система открывается, данные доступны и файлы совпадают. Только после этого считать ежедневный backup пригодным для аварийного восстановления.

## Этап 8. Личная приёмка и показ работы

После технических проверок владелица сама открывает личный чат с тестовым ботом и выполняет короткий сценарий:

1. `/start` → проверить меню и подсказки.
2. Создать тестовый паспорт песни с источником и проектной связью.
3. Приложить тестовый аудиофайл/текст → получить ID и увидеть файл в CRM.
4. Завершить карточку и убедиться, что она осталась в общем каталоге.
5. Получить тестовую утреннюю сводку и напоминание в личный чат.

После её успешного прохождения отдельно показываем цепочку на экране: сообщение/команда → валидация владельца → запись PostgreSQL → вложение в каталог → уведомление → сверка статуса в панели. Тестовый бот и тестовые данные изолируются от рабочего потока.

Текущий Telegram-бот принимает песни, показывает состояние проектов/задач, записывает свободную идею во входящий поток, принимает явную команду создания задачи для указанного проекта и отправляет плановые уведомления. Он пока **не** принимает свободную корпоративную задачу и самостоятельно не выбирает проект/AI-роль и не передаёт работу между проектами. Такой сценарий нельзя демонстрировать как уже готовую возможность: перед полной демонстрацией автономной маршрутизации потребуется отдельная разработка и проверка общего входящего потока задач.

## Согласованные вводные

Владелица выбрала:

1. Сначала пройти тестовый прогон на синтетических данных.
2. Для личной проверки в Telegram создать отдельного тестового бота, чтобы тестовые карточки и сообщения не смешивались с рабочими.
3. Отправлять сводку ежедневно в 09:00 по Москве; если приложение впервые запустилось в этот день раньше планового запуска или после него и сводка ещё не доставлялась, отправлять её при старте. Уникальный ключ события защищает от повторной отправки в тот же день.

Состав текущей сводки: проекты, открытые задачи и сроки, записи в воронке и реестре дохода. Изменения состава можно проверить позже на демонстрации.

Технические секреты, SSH-ключ, токен Telegram и пароль PostgreSQL в чат передавать не надо. Для фактической проверки Telegram они вносятся владельцем непосредственно в `.env` тестовой машины.
