# Telegram и личный сервер: схема запуска v0.1

## Рекомендация

Запускать в два этапа: сначала Telegram как удобный личный вход к существующей локальной CRM песен; после проверки приёмщика — перенос приложения и данных на личный VPS. Для повседневной работы безопаснее закрыть панель частной VPN-сетью, а не публиковать API напрямую. Пока у приложения нет пользовательской аутентификации, размещать его на открытом IP нельзя.

В этом проекте уже есть SQLite-база, локальная веб-панель и Telegram polling-приёмщик. Приёмщик связывает файлы с общей карточкой песни, а не создаёт отдельный каталог на каждый проект. Его кнопки добавлены в код, но для работы бота ещё нужны владелица, которая создаст бота у BotFather и задаст его секреты в окружении запуска. Никакие аккаунты не подключены и сервер не развернут.

## Что будет происходить

1. Владелица открывает бота и нажимает «➕ Новая песня»; бот подсказывает команду `/new Рабочее название`.
2. При необходимости задаёт источник генерации через `/source Название сервиса`, связи с проектами через `/projects P09;P10`, ссылку через `/link URL`, текст/заметку через `/text ...`.
3. Отправляет аудио или документ в активный паспорт. Бот сохраняет файл в общей CRM и возвращает ID карточки.
4. Кнопка «📎 Добавить материалы» подтверждает активную карточку; «⏹ Завершить песню» снимает её с приёма; «📚 Как загрузить пакет» объясняет пакетный экспорт.
5. Если в исходном платном боте уже накопилась история, её нужно экспортировать отдельно из Telegram Desktop или вручную переслать выбранные результаты. Новый бот не может прочитать переписку другого бота и не умеет получать из неё архив задним числом.

Кнопки сейчас — меню Reply Keyboard с текстовыми подсказками. Это не кнопки запуска фоновых работников. Автоматическая ежедневная сводка в текущем приложении формируется планировщиком в 09:00 по Москве, пока работает сам сервис; Telegram-рассылка сводки не подключена. Для неё потребуются отдельная функция отправки, согласованный состав сводки и постоянно работающий процесс.

## Подготовка бота

1. В Telegram открыть BotFather, создать отдельного бота и сохранить выданный токен в менеджере секретов или переменной окружения на компьютере/сервере. Токен не отправлять в этот чат, не класть в Git и не вставлять в скриншоты.
2. Узнать собственный числовой Telegram user ID надёжным способом и передать его только в переменную `TELEGRAM_ALLOWED_USER_IDS` на машине, где запущен приёмщик. В группах бот ничего не обрабатывает; список разрешённых пользователей обязателен.
3. Пока не переносить токен и не запускать приёмщик на публичном хосте. Сначала установить и проверить версию приложения локально вместе с API, затем запускать оба процесса под отдельным непривилегированным пользователем.
4. Для текущего кода сначала запустить API на `127.0.0.1:8787`, затем в другом процессе — `python -m corporate_brain.telegram_intake` из каталога `system/runtime`.

Файлы до 20 МБ бот может скачать через облачный Telegram Bot API. Большие аудиомастера (до текущего лимита CRM 100 МБ) загружать через веб-панель. Для больших архивов старых чатов предпочтителен экспорт Telegram Desktop и локальный импортёр; не отправляйте API-ключи музыкальных сервисов, пароли или приватные переписки.

## Личная инфраструктура и защита

Целевая схема для одного владельца: VPS с поддерживаемой Linux-системой, Docker Compose или systemd, CRM API, отдельный Telegram polling-процесс и постоянный зашифрованный диск/том для базы и медиа. Оба процесса устанавливают только исходящее соединение; webhook и открытый Telegram-порт не нужны. Панель открывается через частную VPN-сеть (например, Tailscale/WireGuard) или через HTTPS с отдельной сильной аутентификацией после её добавления в приложение.

Перед публичным доступом необходимо закрыть следующие пробелы текущей версии:

- добавить аутентификацию и проверку прав на все API-маршруты и загрузки/скачивания;
- хранить файлы и базу в выделенном постоянном каталоге, не в контейнерном слое;
- ограничить SSH ключами, включить обновления ОС, firewall и непривилегированные процессы;
- TLS для любого доступа вне VPN; не открывать порт 8787 всему Интернету;
- хранить токен бота в secrets/environment-файле с правами только владельца, не в исходниках и логах;
- шифровать резервные копии отдельно от сервера, включить расписание и периодически проверять восстановление;
- не загружать клиентские/кандидатские персональные данные без необходимости и без отдельной политики доступа/срока хранения;
- настроить проверку доступности, свободного места и ошибок резервного копирования.

SQLite разумен для текущей личной системы и одного писателя при корректных резервных копиях. PostgreSQL понадобится при нескольких одновременных пользователях/процессах с частыми записями, разграничении прав и дальнейшем росте; менять базу до этого не обязательно.

## Перенос данных

1. Создать резервную копию SQLite согласованным методом SQLite Backup API, затем скопировать целиком `system/runtime/data/` (база, вложения и метаданные), а не только файл базы.
2. Переносить копию по SSH/SFTP или через шифрованный архив; не публиковать архив в GitHub и не пересылать его в открытом канале.
3. На сервере сверить SHA-256 переданного архива, развернуть приложение, восстановить данные и проверить количество проектов, задач, песен, вложений и контрольные суммы файлов.
4. Проверить создание тестовой карточки, загрузку/скачивание тестового файла, доступ только владелицы, автоматический перезапуск после reboot и восстановление копии.
5. До прохождения проверок оставить исходную локальную базу главным источником. После переключения направлять новые записи только в один активный экземпляр, чтобы не создавать расхождения.

Полный экспорт GPT-проектов и старых чатов — отдельный импортный этап. Сервер сам не получит доступ к проектам GPT, Perplexity, Avito, соцсетям или старым чатам; для каждой системы нужен экспорт, поддерживаемый коннектор/API или ручная передача. Не считать эти источники синхронизированными, пока не проверен отдельный работающий обмен.

## Автоматизация по очереди

1. **Уже подготовлено локально:** ежедневная сводка в панели при запущенном сервисе; кнопки приёмщика; регистрация паспорта песни и материалов.
2. **После BotFather:** запустить polling-приёмщик локально на личном компьютере и вручную проверить ввод одного тестового файла. Это удобно, но бот не работает, когда компьютер выключен.
3. **После настройки хоста:** перенести сервис и данные, включить автозапуск после перезагрузки, мониторинг и резервирование. Это обеспечит постоянно доступный бот и панель.
4. **После отдельной разработки:** Telegram-сводки, напоминания по срокам, более удобный пошаговый мастер создания паспорта, сценарий пакетного импорта двух каналов, планировщик публикаций и интеграции с другими платформами.

## Что нужно решить для серверного развертывания

Для конкретного пошагового развёртывания понадобятся выбранный хостинг/VPS (или решение выбрать его), регион хранения, допустимый месячный бюджет и решение о доступе к панели: только личная VPN-сеть или внешний HTTPS-вход. До этих решений безопасный локальный режим остаётся рабочим вариантом; покупать сервер или подключать аккаунты автоматически не нужно.
